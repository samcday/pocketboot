# MSM8916 SMP experiments, 2026-09-11

The first hardware milestone is a repeatable DB410c boot in which pocketpreboot
starts CPUs 1–3 through Qualcomm SCM and ACC, Pocketboot uses all four cores,
and a kexec destination kernel uses the same cores after they are reparked in
the reserved resident page. This requires both boot and handoff evidence;
ordinary PSCI startup is only a baseline. See the [resident ABI](msm8916-spin-table-abi.md)
and [kernel patch notes](../patches/kernel/msm8916/README.md).

The corrected cold-start sequence now passes on DB410c through three consecutive
kexec handoffs, including reentry through packaged pocketpreboot. Every kernel
passed measured work on CPUs 0–3, 40,000 shared-buffer handoffs, and 4,000 checked
CPU migrations. A bounded five-minute repeat run passed all 21 rounds without
reproducing the earlier delayed transport failure. The Samsung device build succeeds, but
Samsung hardware validation remains separate from this DB410c evidence.

## Initial baseline and exploratory sequence

- U-Boot transient FIT loading through `fastboot stage`, then UART `bootm
  93400000`. The running U-Boot download address differs from its source
  defconfig default. `fastboot boot` on this host wraps a FIT in an Android
  image and failed; the board reset back into fastboot.
- A baseline Pocketboot kernel with the DB410c's ordinary PSCI configuration
  brought up four CPUs at EL1 and exposed its fastboot service.
- Four concurrent processes, individually pinned to CPUs 0–3, each checksummed
  the same 64 MiB of generated byte values on their assigned CPU. All returned hash
  `292d74d0d0222325`, consuming approximately 0.504 seconds of CPU time each.
- Serial BREAK followed by SysRq `b` reset that kernel into PBL, U-Boot and
  fastboot, providing a recovery path for a responsive kernel.
- The corrected non-PSCI image completed raw secondary startup. SMC64 was
  unsupported; the SMC32 probe and `SET_BOOT_ADDR_MC` call succeeded. ACC
  startup at `0x0b098000`, `0x0b0a8000` and `0x0b0b8000` brought CPUs 1–3
  into the resident loop, each acknowledging arrival at EL1.
- That kernel accepted the v1 reservation at `0x854ff000`, brought all four
  CPUs online using spin-table, and reached Pocketboot's fastboot service.
  All four pinned workloads passed again. The captured live DTB confirms
  `spin-table` and release addresses `0x854ff400`, `0x854ff480`, `0x854ff500`
  and `0x854ff580` for CPUs 0–3 respectively.
- The first kexec parked CPUs 1–3 with epoch 2 acknowledgments before entering
  the destination. Its separate input DTB originally used PSCI and had no
  parking page. Pocketboot propagated the live contract; the destination
  booted all four CPUs at EL1 and all four pinned workloads passed on UART.
- In the earlier exploratory sequence, a second kexec advanced all three acknowledgments to epoch 3 and again
  booted all four CPUs at EL1. Its live DT snapshot confirms all four
  spin-table release addresses. A later USB/shell failure in this kernel
  remains unexplained; serial SysRq still reset it into U-Boot.
- Load-only negative targets with a disabled CPU or an overlapping reserved
  region were rejected before shutdown.

The baseline kernel Image SHA-256 is

## Implementation and current investigation

The recovered code now has a versioned reserved-page protocol shared between
pocketpreboot, Linux spin-table CPU operations and the Pocketboot kexec FDT
loader. The patched DB410c and A5U kernels build. The resident assembly has
also passed a separate Cortex-A53 QEMU test, before the later SMPEN gate, for initial acknowledgment,
release, re-entry and acknowledgment of a second generation. QEMU startup
uses its CPU_ON facility only in that test harness; it does not test the
Qualcomm firmware or ACC registers.

The early hardware failure exposed a separate relocation defect: Rust emitted
absolute pointers in read-only tables, while the shim was linked at zero and
loaded at `0x80000000` without runtime relocation. PIC/PIE linking and startup
handling of `R_AARCH64_RELATIVE` resolved it. The successful shim SHA-256 is
`975d567ee0f322bf68beec44ae9a89136ce1a9e7168edde03b5b68083b12fa52`.
The later corrected sequence below verifies both repeated kernel parking and
packaged-preboot reentry on hardware.

The later test exposed a defect in the original workload when built with `-Os`:
the compiler reused the parent's calculation in children. Consequently
`generation-2-snapshot.log` is **not evidence of work on all four cores** despite
its old PASS string; its negligible CPU time and missing result lines invalidate
that measurement. Earlier `-O2` traces separately show four measured ~0.5-second
results. Workload V2 uses a volatile seed, transports child results to a single
parent writer, and requires four distinct CPU results with more than 0.02 seconds
of measured CPU time apiece. It has now passed in all four kernels of the
corrected sequence. Register arithmetic alone does not prove cache coherence;
the separate shared-buffer and migration checks also passed in each kernel.

The raw entry path, lk2nd and the U-Boot reference all rely on firmware to set
Cortex-A53 `CPUECTLR.SMPEN`. Our kernel exit preserves that register. Read-only
snapshots now show `CPUECTLR=0x40` on CPU0 and all three secondaries during cold
startup and again on packaged reentry after three kexecs. This verifies SMPEN
for this firmware and sequence. No attempt is made to write that register.

## Other observations

Outgoing kernels warn in FunctionFS teardown before CPU parking. The
pinned kernel's unmount path calls `cancel_work_sync` on a work item that can
remain uninitialized. Upstream commit
`3137b243c93982fe3460335e12f9247739766e10` fixes this exact callchain by moving
initialization into `ffs_data_new`; the affected files in our source match the
unmodified v7.1-rc6 base. This is separate from the new parking code. It was subsequently backported
as patch `0003` during the [A5 validation](a5u-smp-experiments-2026-09-11.md);
the DB410c recordings below predate that backport.

One 66-byte inline host fastboot command exceeded Pocketboot's 64-byte command
limit and stalled the USB exchange. The live kernel still ran the four-core
workload over UART, and unbinding/rebinding its USB gadget recovered fastboot
without a reboot. Use staged scripts for longer commands. The later generation-2
failure occurred during a short staging command and must not be assumed to have
the same cause.

SysRq reset retains the resident page's marker in DRAM. Cold preboot therefore
refuses another raw startup at that address until a genuine cold power cycle;
it does not overwrite an occupied page based merely on a bootloader reset.
Guarded reentry is only for an explicitly matching live spin-table handoff with
zero release slots and matching request/acknowledgment generations.

The A5U Android boot image builds successfully. Wrapped image packaging now
covers the inner kernel's full runtime footprint, including its otherwise
absent BSS, while preserving the outer header needed to locate the payload.
The Samsung hardware path has not been tested in this experiment.

## Corrected cold start and three handoffs

Sam cold-power-cycled the board. A read-only U-Boot check then showed `0xaa`
throughout the former descriptor, replacing the old `spin-tab`/`PBSPIN01`
markers. No occupied page was cleared or rewritten to bypass the startup guard.

`target/db410c-lab/20260911/nonpsci-coherency/image.itb` was the cold-start
FIT. Its shim SHA-256 is
`5f87eb4bd5ee2b9591c26f645cb132adca48f9cc8fd4166d25681fbc642de561`.
It reports the primary and secondary CPUECTLR values, requires SMPEN, and tags
optional secondary snapshots with `PBSDIAG1` as documented in the ABI. Fifteen
host tests and the startup relocation smoke pass. QEMU's Cortex-A53 model reads
zero for CPUECTLR, so the latest exact resident test proves zero-SMPEN reporting
and refused release; it does not claim a new positive release run under that
model.

The `kexec-coherency/` artifact directory has V2 arithmetic tests and three
destination images, including the latest preboot as generation 3. It also has
`coherency-install/*.sh` and `coherency-run.sh` to install and run the separate
shared-buffer and migration test via short staged fastboot commands. These
images and diagnostics have now passed on DB410c. The two
12-second test phase limits fit Pocketboot's 30-second staged-shell limit.
See the [handoff runbook](db410c-kexec-validation.md) and
[coherency test runbook](msm8916-coherency-validation.md).

UART records CPU1, CPU2 and CPU3 acknowledgments at each outgoing epoch before
`Bye!`, followed by four CPUs online in each new kernel. Generation 3 prints
`reusing acknowledged resident CPUs` and reports `CPUECTLR=0x40` for all cores;
its reentry segment contains no SCM/ACC startup sequence. All four captured live
DTBs have the same exact release addresses and reservation, with PSCI disabled.
Destination images initially supplied separate PSCI DTBs without that page,
so this also verifies propagation of the live contract through the real loader.

`tools/db410c_check_phase.py` reproduces the measured checks, verifies artifact
hashes, keeps inline commands within 64 bytes, and saves the snapshot, live DTB,
kernel log and every fastboot result. Current proof is under
`target/db410c-lab/20260911/coherency-proof/`; the continuous boot and handoff
trace is `uart-coherency-full-sequence.log`. A separate UART capture covers the
bounded repeat run. USB reconnection alone is not used as a pass criterion.

The repeat run completed 21 rounds over 300.8 seconds, beginning at kernel
uptime 117.69 seconds. Each round passed the same four measured CPU workloads,
40,000 buffer handoffs and 4,000 migrations. Across the four boot phases and
repeat run this totals 1,000,000 verified shared-buffer handoffs and 100,000
checked migrations. The final kernel remained responsive in Pocketboot
fastboot; its clocksource was `arch_sys_counter`. No new UART diagnostic
appeared during the repeat run. This is a bounded result, not a claim of
long-duration stability or a diagnosis of the earlier isolated failure.

The goal's core startup/use/repark/handoff sequence is verified on DB410c.
EL2 parking, ordinary CPU hotplug and crash-kexec remain unsupported by design;
Samsung firmware/hardware acceptance is not implied by the A5 build. The known
upstream FunctionFS warning and warm-boot retained-page limitation remain
documented follow-ups rather than hidden test failures.

## Reproduction conventions

The DB410c fastboot serial is `bc72e60`. UART is the FT232R link ending in
`A50285BI-if00-port0` under `/dev/serial/by-id/`, at 115200 baud, 8N1. Commands
need pacing; `tools/db410c_uart.py` sends at 5 ms per character and captures
raw received bytes to a new file. A single process must own the UART.

`tools/db410c_fit.py` packages a supplied uncompressed Image, prepared DTB,
and optional pocketpreboot binary without changing the board. Its manifest
records hashes of every input and the resulting FIT. The lab layout loads
preboot at `0x80000000`, its kernel at `0x80200000`, and initially supplies
the DTB at `0x85000000`; U-Boot relocates the DTB before entry.

The raw startup input DTB reserves the v1 page at `0x854ff000` and marks all
CPUs with `pocketboot,msm8916-acc` so that a preceding bootloader does not
start them automatically. Only pocketpreboot rewrites this into `spin-table`
after preparing the resident protocol. The kernel command line includes
`console=ttyMSM0,115200n8 earlycon loglevel=7 panic=0` and a unique lab marker.

No persistent flash, erase or U-Boot environment save is needed for these
experiments. A manual power cycle remains necessary for a failure that leaves
neither the UART recovery path nor fastboot responsive.
